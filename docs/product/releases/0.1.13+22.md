### Second cut of the same version - and why the version code did not move

This bundle replaces the one built at 08:11 today
(`b6e41353...ef877`, 82.3 MB). **The version code stays at 22 because the first
bundle was never published** - nothing on any track carries it, so nothing on
any device can be confused by a different artefact wearing the same number. A
version code exists to order releases for Play, and the first cut never entered
that order.

The rule this is a case of, rather than an exception to: bump the version code
the moment a bundle has been *uploaded*, and only then. What changed between
the two cuts is everything under *Play technical quality* below, which is a
manifest change and three new source files - not a rebuild of the same source.

version, package and SDK levels are read from

and the three ABIs from `base/lib/` inside the archive itself. That manifest

### One thing to know before you build this yourself

The first attempt at this bundle failed, and not because of anything in `lib/`:

```
error: package dev.flutter.plugins.integration_test does not exist
```

`android/app/src/main/java/io/flutter/plugins/GeneratedPluginRegistrant.java`
is generated and untracked. A debug or test run writes one that registers
`integration_test`, which is a dev dependency and is not on the release
classpath; the release build then reuses that stale file. Deleting the file
lets Flutter regenerate it correctly. It only ever appears when a release build
follows a test run, which is exactly the order a release goes in.

It caught this second cut too, or would have: the compliance work above was
verified with `flutter test` and a Gradle Kotlin compile, so the stale file was
sitting there again. Deleted before building rather than after failing.

One theme, and it is the oldest part of the app: the dictionary.

It has held 1200 published entries for some time. It was also, for most of
them, unusable. 478 of those entries share a spelling with another entry and
were drawn as identical rows with nothing to tell them apart. 785 of them
contain a letter that does not exist on a phone keyboard, and the search box
compared what you typed with `contains` - so if you had heard `dɩ`, could not
type ɩ, and did the only thing available, the dictionary told you it had no
matching words. Sorting put every word beginning ŋ, ɔ, ɛ, ɩ or ʋ in a heap
after z, where nobody scrolls.

None of that was a bug anybody had filed. It is what a dictionary written for
English does when it is handed a Gur language, and it took reading the data
rather than the code to see it.

There is a second strand in this build, and a member will not see any of it.
Google's August 2026 announcement set two enforcement dates - February and
April 2027 - and one of the three requirements behind them applied to this app
and was not met. Everything in the *Play technical quality* sections below
exists because of that, and none of it changes anything on screen. It is here
because the consequence for missing it is reduced store visibility, which for
an app people mostly arrive at through search is close to the same thing as
being removed.

## Full change list

### New - a dictionary you can search in Kasem

- **Type what your keyboard can reach.** `foldForSearch` maps every extended
  Kasem letter to its nearest keyboard equivalent - ɩ→i, ʋ→u, ə→e, ɔ→o, ŋ→n,
  ɛ→e - and strips tone marks, on both the query and the entry. `di` finds
  `dɩ`; `mani` finds `maŋɩ`; `bunu` finds `bʋŋʋ`. This is the change that
  matters most in the release: 785 of 1200 headwords carry at least one of
  those letters, ɩ alone appearing in 640, so for two thirds of the archive
  the search box did not work at all.

- **Tone marks are dropped for search and nowhere else.** Kasem is tonal and
  the marks are meaningful, which is exactly why they are stripped *here* and
  in no other code path. A learner typing from memory has no idea which tone
  they heard, and an archive that insists they get it right before it will
  show them the word is not a dictionary, it is a quiz.

- **Results are ranked, not just filtered.** `searchRank` scores every entry
  0-5: exact headword, exact rendering, exact meaning, prefix, meaning prefix,
  then anything else searched. Before this the list was filtered and left in
  alphabetical order, so typing `ni` returned every entry containing those two
  letters anywhere - headword, gloss, dialect or rendering - and the entry
  actually headed `ni` could sit fifty rows below a word whose English meaning
  happens to contain "opinion".

- **The plural and the definite form are searchable.** `matches` covered
  headword, meanings, renderings and dialect and stopped. A learner meets a
  word in a text in its inflected form far more often than in the citation
  form a dictionary files it under, and typing what they actually read
  returned nothing for a word the archive holds.

- **The query is folded once per keystroke, not once per entry per keystroke.**
  `rankFor` takes an already-folded query. At 1200 entries that is the
  difference between a search that keeps up and one that stutters on the UI
  thread.

### New - words spelled the same way are told apart

- **mo¹ and mo².** `homographIndex` is assigned once, on the server, at first
  publication, and never reassigned. It is an identity rather than a fact about
  the language: a learner writing `mo²` in their notes, a member sharing an
  entry, Kawuri quoting a sense - all of them are citations, and a citation
  whose target moves is worse than none. A withdrawn number is never handed out
  again, so the numbering under a spelling can read 1, 3. That gap is correct,
  and closing it would point every existing citation at a different word.

- **Stored number, derived superscript.** Whether the number is *drawn* is a
  separate question from what it is, and it depends on how many entries share
  the headword. A word alone under its spelling renders bare - a solitary `mo¹`
  promises a `mo²` that does not exist - and starts showing its `¹` the day a
  second one is published, without anything rewriting it. This is the opposite
  of the call in `kasem-morphology.ts`, where the indefinite particle is derived
  and never stored, and the difference is the point: `mo` after a noun is a rule
  about the language, while a sense number is an arbitrary label nothing can
  re-derive.

- **The number is never part of the headword string.** Two reasons, both
  load-bearing. `indefiniteForm(headword)` appends the particle `mo`, so folding
  the number in produces `nia¹ mo` - not a word, and a false statement about the
  language on a screen built to teach it. And U+00B9 SUPERSCRIPT ONE is Unicode
  category No, a *number*, so it survives `normaliseWord`'s edge strip and would
  have travelled into the tap-a-word index and the backend's exact-match queries,
  where a member typing the plain word would stop finding it.

- **Tapping a word in a post offers the senses.** `dictionaryIndexProvider` was
  `index[headword] = entry` - a plain map, last write wins. The eight entries
  headed `ni` collapsed to whichever one a Firestore snapshot happened to write
  last, and the other seven were unreachable from the tap-a-word feature
  entirely; a reader could be shown a different one an hour later. The index is
  now a list per spelling, and tapping a word with more than one sense opens a
  chooser rather than a confident answer to a question it did not understand.

- **The entry screen says which of several it is,** in words as well as in a
  superscript: "Sense 2 of 8 words written ni. They are different words, not
  different meanings of one word." The convention is three centuries old and a
  learner may never have met it.

- **Kawuri stops merging two words into one.** The dictionary briefing carries
  the sense numbers and, where any are numbered, an explicit instruction:
  these are separate entries that happen to be written the same way, give each
  its own meaning, never say one "also means" what belongs to the other. Handed
  two lines both headed `mo`, the reasonable reading is one word with two
  meanings - which is exactly the error the numbering exists to prevent.

- **A migration, because the invariant has to hold for the whole collection.**
  `backfill-homographs.mjs` gives all 1200 existing entries a `headwordKey` and
  a number, oldest first by `createdAt`. It is idempotent - an entry that
  already carries a number keeps it - which matters more than it looks: a
  migration that reshuffled numbers on its second run would break every note
  and saved word that had quoted one. It counts unpublished rows too, so a
  withdrawn number is not handed out again.

### New - Kasem alphabetical order

- **ɛ after e, ɩ after i, ŋ after n, ɔ after o, ʋ after u.** `collationKey`
  gives every letter a two-character weight - base letter, then rank within it
  - so comparing the keys gives the right order with no custom comparator.
  `String.compareTo` is UTF-16 code-unit order and every extended Kasem letter
  lives above U+0100, so the old sort filed several hundred words after z and
  put `lagɩ` after `lagz`.

- **The list order is total and repeatable.** Headword, then sense number, then
  document id. Dart's `List.sort` is explicitly not stable, so the 478 entries
  sharing a spelling had no defined order and could come back in a different one
  from two snapshots carrying the same documents - reordering numbered senses
  under a reader's finger.

- **One position is admitted as uncertain.** `ə` is filed at the end of the
  e-group. The sources this project has do not settle where it belongs, so the
  choice is documented as a single line to change rather than presented as
  established.

### Changed - the dictionary stops writing its own empty states into the data

- **Placeholders are out of the data fields.** The reader filled empty fields
  with sentences describing their own emptiness - `'Translation pending'`,
  `'No example yet'`, `'No written guide yet'`, `'No translated example yet'`.
  Those were not merely displayed: they were the entry's data, so every
  `if (entry.example.isNotEmpty)` guard in the app was permanently true and
  each card rendered its own apology as though it were content. An entry with
  no sentence drew a card headed Example containing two lines reading "No
  example yet" and "No translated example yet". The fields are honestly empty
  now, which is what lets the guards mean something and what makes a sparse
  entry shorter rather than padded.

- **`'Translation pending'` was also a searchable meaning.** It went through
  the same splitter as a real gloss, so `entry.matches('pending')` was true and
  the entry carried a placeholder as its one and only meaning.

- **An entry with no Kasem side is no longer invented into one.** The reader
  fell back to the literal headword `'Kasem entry'`, which then entered the
  tap-a-word index as the English words "kasem" and "entry" - so a reader
  tapping the ordinary word "entry" in a post was shown a dictionary card. A
  row with no headword cannot be looked up, said aloud or taught; it is a
  broken row, and hiding it is more honest than dressing it as a word.

- **Governance boilerplate is no longer "Cultural context".** All 1200 imported
  rows carry one identical sentence about spelling and register requiring
  community review before publication, and it was rendered on every entry under
  a heading that promised something about the culture. Suppressed by shape
  rather than exact string, so a reworded re-import does not put it back.

- **No more "Kasem" beside "Kasem".** The dialect fallback was the literal
  string `'Kasem'`, so any entry with no recorded dialect drew a pin icon
  labelled Kasem next to a globe icon labelled Kasem.

- **The entry always reflects the live document.** The screen short-circuited
  on an entry handed in by its caller and never watched Firestore, so a word
  that had since been corrected, gained a recording, or been unpublished kept
  rendering from whatever the caller was holding.

- **The headword can be selected and copied.** It was an inert `Text`, on a
  screen whose whole purpose is a word somebody wants to use. The sense number
  is deliberately outside the selection: `dɩ²` pasted into a message is not a
  word.

- **The two "+N" badges on a list row no longer look identical.** One counts
  alternative Kasem spellings and the other counts English senses; they were
  the same colour, size and weight, three pixels apart. The first now says
  "+2 forms".

- **The screen-reader label carries the word class.** It composed headword,
  renderings and meanings and dropped the one line that actually tells eight
  entries headed `ni` apart.

### New - the contribution form has a second pair of eyes

- **`reviewContributionDraft` checks a draft before it is sent.** Advice only.
  There is no severity above "ask", the send button never consults it, and a
  check that fails to load leaves the form exactly as it was. A form that could
  refuse a speaker's own word would have put a heuristic above the people the
  archive exists to record.

- **The check that had never been possible: "8 other words are spelled ni".**
  A contributor sending a ninth `ni` had no way to know the dictionary already
  held eight, so it arrived looking like a duplicate and a reviewer had to
  guess which it was. The contributor is the only person who can answer, and
  now they are asked - naming the existing senses with their numbers, and
  saying plainly that nothing is overwritten.

- **Same word, same meaning, already published** is raised as a question with
  the existing entry named, and points at sending a correction instead.

- **The boxes being the wrong way round is caught** - a common English word in
  the Kasem box, Kasem letters in the English box, or both boxes holding the
  same text. The English word list is deliberately tiny and all function words:
  a false "you have put English in the Kasem box" aimed at a speaker writing
  their own language is a far worse error than missing a genuine slip.

### Removed - synthetic content

- **The demo dictionary is gone.** `DemoDictionaryRepository` held four
  invented entries - "Kasem greeting · demo", "Synthetic example withheld",
  "Validated community data will replace this demo" - and `EntryDetailScreen`
  consulted it *before* Firestore, so `/entry/demo-water` resolved to invented
  vocabulary in preference to a real published document with the same id.

- **`isSynthetic` defaulted to `true`,** so any entry built without explicitly
  passing `false` was flagged in the interface as a demo projection. The field
  is gone with the data it described.

- **`HomeScreen` is deleted.** Unreachable - no route, not one of the five rail
  destinations - and its whole body was demo-shaped: a "TODAY'S WORD · DEMO"
  card, a search over the synthetic entries, and a "Development build · sample
  data" banner.

- **Explore's curated preview is gone.** Three invented creators -
  `@afi.dances`, `@kassena.collective`, `@heritage.in.motion` - over Unsplash
  stock photographs, carrying fabricated engagement counts of 12,800 likes and
  426 comments, shown to every guest on first launch and to everybody whose

  not have.

- **The preview comment sheet went with it,** including two invented community
  members under a fabricated reply count, and a reply box that answered "Your
  local Kasem reply was added to this preview" and then discarded what was
  typed.

- **For You now has its own empty state.** Removing the preview would otherwise
  have dropped it onto the Following copy - "Follow a creator and their reels
  arrive here", under a button switching to the tab the member is already
  standing on. It says nothing has been published yet, and offers no button
  that leads nowhere.

### New - Play technical quality: Zero-Tap Sign-In

Play's April 2027 rule is that an app supporting sign-in must restore the
session on a member's next Android device **without a tap**. Games are exempt;
so are enterprise apps and Block Store integrations finished before 30
September 2026. None of those apply here, and nothing in the app did this.

- **The mechanism is a restore key, not a stored token,** and that distinction
  decided the whole shape of the work. A restore key is a real public-key
  credential: the private half is minted into the device's credential store and
  never leaves it, Android's backup transport carries it to the next handset,
  and what reaches the backend is a signature over a challenge it issued
  moments earlier. A "restore token" sitting in Firestore would have been a
  bearer credential for somebody's account, in a database, forever.

- **So the backend is a WebAuthn relying party.**
  `services/functions/src/restore-credentials.ts` adds five callables -
  `startRestoreKeyRegistration`, `finishRestoreKeyRegistration`,
  `startRestoreSignIn`, `finishRestoreSignIn`, `forgetRestoreKey` - verifying
  attestations and assertions through `@simplewebauthn/server`, the one new
  runtime dependency in this release. A verified assertion buys exactly one
  thing: a Firebase **custom token** for the uid the credential was registered
  to. The app exchanges it for an ordinary session, so every rule and claim
  downstream is untouched.

- **Three server-only collections,** named in `firestore.rules` rather than
  left to the default deny, because a collection that authenticates people
  deserves to be findable in that file. `_restoreCredentials/{uid}` holds the
  public half; `_restoreCredentialIndex/{credentialId}` maps a credential back
  to a uid, which is needed because a restore sign-in arrives unauthenticated;
  `_restoreCredentialChallenges` is single-use anti-replay state.

- **The device half is written here, not taken from pub.dev.**
  `RestoreCredentialChannel.kt` wraps Credential Manager's create, get and
  clear, for the same reason `PlayIntegrityChannel.kt` does: a plugin in that
  position could hand back an assertion from somewhere else, and would need
  re-auditing on every upgrade for the life of the project. It adds
  `androidx.credentials:credentials` and `-play-services-auth` 1.6.0, and is
  gated to Android 9 - which is the API's own floor, not a shortcut.

- **Signing out forgets both halves, device first.** `AuthRepository.signOut`
  clears the key before it ends the session, because a sign-out that left the
  key behind would be a sign-out in name only: the next launch would silently
  restore what the member had just closed.

- **A restore is attempted once per launch, and only after the auth state has
  actually resolved.** `authStateChanges` has emitted nothing on the first
  frame, so an unresolved stream reads as "signed out" - acting on that would
  fire a restore on every cold launch of a member who was already signed in.

- **None of it is visible and all of it fails quietly.** Android below 9, stale
  Play services, no screen lock, backup switched off, a device set up from
  scratch - every one of those ends at the ordinary sign-in screen, which is
  what happens today.

- **It is dormant in this build.** Credential Manager will not mint a key until
  the live `assetlinks.json` claims
  `delegate_permission/common.get_login_creds`, and today it claims only
  `handle_all_urls`. See *Deploying this one*.

### Changed - Play technical quality: the app takes part in Android backup again

- **`android:allowBackup` was `false` and is now `true`,** because the restore
  key travels by the backup transport and an app excluded from backup is one
  the transport carries nothing for. This is the only member-affecting change
  in the compliance work, and it is a real change in posture rather than a flag
  flip.

- **Both rule files are whitelists with one entry.**
  `res/xml/backup_rules.xml` for Android 11 and below,
  `res/xml/data_extraction_rules.xml` for 12 and above, each naming
  `FlutterSharedPreferences.xml` and nothing else. Appearance, reading
  language, data-saver choices, recent searches and Kawuri history follow a
  member to their new phone. Everything else stays behind, and each omission is
  a decision: `FlutterSecureStorage.xml` is encrypted with hardware keystore
  keys that are not backed up and cannot be, so a restored copy is unreadable
  ciphertext; the Firebase Auth session store belongs to the install that
  obtained it; `databases/` indexes downloaded files by path and those files
  are not restored; `files/` is the downloaded media itself.

- **One consequence worth knowing:** because preferences *are* restored, the
  marker recording "this install already minted a key" is kept in the secure
  store instead. In preferences it would arrive on the new device claiming a
  key that device does not have, and no key would ever be minted there.

### Changed - Play technical quality: bitmaps are released on the way out

Play measures bitmap memory per app state from February 2027 and treats more
than 200 MB outside the foreground as bad behaviour. This app is more exposed
to that than most: the music player runs a media foreground service, so it has
a long-lived *user-perceived service* state that an app without background
playback never enters - somebody listening to an audiobook with the phone in a
pocket is in it for hours.

- **Flutter only half handles this.** The engine forwards Android's
  memory-pressure signals and `handleMemoryPressure` empties the image cache
  when one arrives, but those signals mean "the device is running low" and are
  not sent when an app is merely backgrounded. So the cache survived it, at up
  to its full 100 MB budget, for as long as the process did - which is exactly
  the state being measured.

- **`core/image_memory.dart`** attaches a lifecycle observer in `main` that
  clears the image cache when the app leaves the foreground. Images a live
  widget still holds are untouched, so what goes is the backlog rather than the
  screen; the cost of being wrong is a re-decode on the way back in.

### Unchanged - DEX optimisation was already compliant

Worth recording so nobody "fixes" it later. Play's other February 2027 rule is
at least 25% coverage across optimisation, shrinking and obfuscation, and this
build already meets it: the Flutter Gradle plugin sets `isMinifyEnabled` and
`isShrinkResources` on the release build type itself (only `-Pshrink=false`
turns that off, and nothing here passes it), AGP 9 is pinned in
`settings.gradle.kts`, and `-repackageclasses ''` is in `proguard-rules.pro`.
The dynamic-memory thresholds are not close either - the floor case allows 2 GB
foreground on a 4 GB handset. Full reasoning in
`docs/product/play-technical-quality-2027.md`.

## Deploying this one

Order matters, and the middle step is the one that is easy to forget.

1. `npm run build:functions`
2. Regenerate `services/functions/functions.yaml` before deploying. A stale
   manifest silently skips new triggers, and this release adds six:
   `reviewContributionDraft` and the five Zero-Tap callables. There is no such
   file in the tree today; delete it if one appears.
3. `firebase deploy --only functions`
4. `firebase deploy --only firestore:rules` - the three server-only
   `_restoreCredential*` collections.
5. `node services/functions/scripts/backfill-homographs.mjs` (dry run first;
   it prints the busiest spellings and how many entries it would number), then
   `--commit`.

The backfill is not optional. Until it runs, `creators.ts` cannot see the
existing entries when it queries for peers - it groups on `headwordKey`, which
no legacy row carries - so a new sense of `ni` would be handed the number 1
while eight `ni` entries already exist, and the display would number the new
one while the eight stayed bare.

### Zero-Tap Sign-In needs two more things, and neither is a deploy

The first is done. The second is safe to leave undone - the feature reports
itself disabled and the app behaves exactly as it does today - so this release
can ship without it.

**~~One relation on the live `assetlinks.json`.~~ Done - 2026-09-05.**
`indigenworld.com` now claims `delegate_permission/common.get_login_creds` for
`com.indigenworld.indigen`, confirmed through Google's Digital Asset Links API.

It was not the out-of-band file edit this section originally described, and the
reason is worth keeping. That file was never uploaded by anyone: Firebase
Hosting *generates* an assetlinks.json from the Android apps registered in the
project and serves it whenever the site deploys none of its own. It arrives
`private, no-store` with no HSTS, because it never passes through the `headers`
rules in `firebase.json` - which is how you tell it from a deployed one.
Firebase cannot be asked to add a second relation, so the site now serves its
own file, built from `apps/website/config/app-links.json` with each Android app
listed separately (the four packages are signed by different keys). It
reproduces the generated file exactly plus the one relation; the deploy
uploaded a single file.

The cost, which outlives this release: a deployed file overrides generation
permanently, so a new flavour or a rotated signing key must be added to that
config by hand or App Links silently stop verifying for it.

**Two environment values,** in `services/functions/.env`:

```
RESTORE_CREDENTIAL_RP_ID=indigenworld.com
ANDROID_CERTIFICATE_DIGESTS=J5bEcASyi9-sqO8XBPxNl77bERWNgxoGXtuszt3qoj8,IlpLTH53NMIwxyu4xXFOPPuydAAffqh-bf4wBq10vEQ,hU2KXfAX136gOXjM-T62ZBMi1EhkoDvunx_AcSczfUA,o6uNPjXaFW9_SVLX71kTRSfV6ed14G5rhTS79RLTvVw
```

Those four are the production package's own fingerprints from the live file,
converted to the base64url form Credential Manager sends; the colon-hex from
Play Console is accepted verbatim too, and they are written out only so nobody
has to convert them by hand.

`ANDROID_CERTIFICATE_DIGESTS` is reused rather than duplicated - it is the list
Play Integrity already checks against, and a second copy is a second thing to
forget on a key rotation. Two consequences of that. It is **currently unset**,
so Play Integrity's certificate check is being skipped; setting it switches
that on, which is right but is a behaviour change in a second feature, and Play
Integrity should stay on `monitor` while it beds in. And only the production
certificates are listed, so a `.dev` or `.staging` build will not do zero-tap -
adding those digests would also make Play Integrity accept them, which is the
worse trade.
